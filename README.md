# Aegis

**Zero-Trust Access Control & Clearance Management Portal.** A security-focused full-stack
project for managing who may enter which physical zone, based on role, clearance tier, and
explicit time-bound grants, with a tamper-resistant audit trail. The finished system will
put a FastAPI API and a React UI behind a hardened Nginx edge, with PostgreSQL and Redis on
an internal network.

> **Status: work in progress. The foundation is complete; auth, the policy engine, the
> audit chain, and the UI are still being built.**
> Today the repo contains the database schema and its integrity guarantees, the
> configuration layer, the container/edge setup, and the CI pipeline definition. It has no
> login, no API endpoints beyond a health check, and the UI is a status page. Everything
> unbuilt is listed under [Roadmap](#roadmap-not-yet-implemented). Every number in this file
> was measured by a command shown in [How these were measured](#how-these-were-measured).

## What's implemented today

| Area | What exists (and was verified) |
| --- | --- |
| **API app** | FastAPI app factory (`app/main.py`) with CORS and `GET /api/health`. OpenAPI/docs are disabled when `ENVIRONMENT=production`. The v1 router is mounted but has **no routes yet**. |
| **Fail-fast config** | `pydantic-settings` (`app/core/config.py`). The app refuses to start if `JWT_SECRET`, `BADGE_HMAC_SECRET` or `MFA_ENCRYPTION_KEY` is missing, shorter than 32 chars, or still set to the `.env.example` `CHANGE_ME` placeholder. It also refuses to start if `MFA_ENCRYPTION_KEY` isn't a valid Fernet key, or if `COOKIE_SECURE=false` while `ENVIRONMENT=production`. Secrets are `SecretStr`, and validation errors never echo the rejected value (`hide_input_in_errors`). |
| **Data model** | 7 SQLAlchemy 2.x models with UUID primary keys (`gen_random_uuid()`), timezone-aware timestamps, and native PostgreSQL enum types for role, clearance, visitor type/status, access result, and subject type. |
| **DB integrity** | 10 `CHECK` constraints, e.g. a zone access grant must reference **exactly one** of user/visitor, occupancy must stay ≤ capacity, and audit hashes must be 64-char lowercase hex. Foreign-key delete behaviour is chosen per relation (see below). |
| **Migration** | One Alembic migration, autogenerated and then reviewed by hand. Enum types are created and dropped explicitly, so `downgrade base` → `upgrade head` round-trips cleanly (covered by a test). The backend container runs `alembic upgrade head` on start. |
| **Append-only audit table** | The `audit_log_immutable` PostgreSQL trigger rejects every `UPDATE`, `DELETE` and `TRUNCATE` on `audit_logs`, including statements that match zero rows. [Proof below](#proof-the-audit-trigger-blocks-mutation). |
| **Clearance ordering** | `Clearance` is an `IntEnum` (`Reliability`=1 < `Secret_Level_II`=2 < `Top_Secret`=3). `held.satisfies(required)` raises `TypeError` on anything that isn't a `Clearance`, so a stray `int` or string can't be compared silently. The PG enum is declared in the same order, so DB-side comparisons agree. |
| **Containers** | Multi-stage Dockerfiles for backend and frontend. **Every process in the stack runs as non-root** (measured uids: backend 10001, frontend/edge nginx 101, postgres 70, redis 999). |
| **Compose hardening** | `no-new-privileges` on all services. `cap_drop: [ALL]` and a read-only root filesystem on backend, frontend and edge nginx. Postgres and Redis sit on an `internal: true` network with no host ports, and Redis requires a password. Compose refuses to start if a required secret variable is empty. |
| **Edge (Nginx)** | Single entry point on `:8080` with a CSP, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` and COOP headers. `limit_req` rate limiting is applied at the edge (20 r/s, burst 40 on `/api/`; observed working, see Metrics) and `client_max_body_size 1m`. |
| **Frontend** | Vite + React + TypeScript + Tailwind build, served by unprivileged Nginx. Currently a single page that shows live API health. |
| **CI pipeline** | `.github/workflows/devsecops.yml` defines 4 jobs: `secret-scan` (gitleaks); `backend` (ruff, ruff format, mypy, bandit, pip-audit, pytest + coverage); `frontend` (oxlint, build, npm audit); `containers` (image build for backend and frontend, non-root check, Trivy image and config scan, `fail-fast: false`). The backend job runs the 8 integration tests against a `postgres:16` service container; in CI they fail rather than skip if the database is missing. Test secrets are generated randomly per run, and third-party actions are pinned to commit SHAs. **The first run (commit `ea88255`) failed** on gitleaks and Trivy; the fixes are verified locally but haven't been re-run on GitHub yet (see Known limitations). |

### Foreign-key choices

| Relation | On delete | Why |
| --- | --- | --- |
| `audit_logs.actor_id → users` | `RESTRICT` | An actor with audit history can't be hard-deleted; deactivate instead. `SET NULL` would be an `UPDATE`, which the trigger blocks anyway. |
| `zone_access_grants.granted_by → users` | `RESTRICT` | Keeps accountability for who granted access. |
| `visitors.host_user_id → users` | `RESTRICT` | A visitor always has a responsible host. |
| `zone_access_grants.{user_id, visitor_id, zone_id}` | `CASCADE` | A grant is meaningless without its subject or zone. |
| `badges.visitor_id → visitors` | `CASCADE` | A badge belongs to exactly one visitor. |
| `access_events.zone_id → zones` | `SET NULL` | Access history survives removal of a zone. |

## Proof: the audit trigger blocks mutation

Run against the stack's PostgreSQL 16.15 container (migrated by the backend on startup), after
inserting one valid row:

```text
$ docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -e 2>&1' <<'EOF'
UPDATE audit_logs SET action = 'tampered' WHERE id = 1;
DELETE FROM audit_logs WHERE id = 1;
TRUNCATE audit_logs;
SELECT id, action, left(entry_hash, 12) AS entry_hash FROM audit_logs;
EOF
UPDATE audit_logs SET action = 'tampered' WHERE id = 1;
ERROR:  audit_logs is append-only: UPDATE is not permitted
HINT:  Audit entries can only be inserted.
CONTEXT:  PL/pgSQL function audit_logs_reject_mutation() line 3 at RAISE
DELETE FROM audit_logs WHERE id = 1;
ERROR:  audit_logs is append-only: DELETE is not permitted
HINT:  Audit entries can only be inserted.
CONTEXT:  PL/pgSQL function audit_logs_reject_mutation() line 3 at RAISE
TRUNCATE audit_logs;
ERROR:  audit_logs is append-only: TRUNCATE is not permitted
HINT:  Audit entries can only be inserted.
CONTEXT:  PL/pgSQL function audit_logs_reject_mutation() line 3 at RAISE
SELECT id, action, left(entry_hash, 12) AS entry_hash FROM audit_logs;
 id |   action    |  entry_hash
----+-------------+--------------
  1 | system.init | aeebad4a796f
(1 row)
```

It is a single `BEFORE UPDATE OR DELETE OR TRUNCATE ... FOR EACH STATEMENT` trigger that raises
SQLSTATE `23001`. The same behaviour is asserted in `backend/tests/test_migrations.py`.

### Data model (7 tables)

```text
users ─┬─< visitors            (host_user_id, RESTRICT)
       ├─< zone_access_grants  (user_id CASCADE; granted_by RESTRICT)
       └─< audit_logs          (actor_id RESTRICT, nullable for system events)

visitors ─┬─< zone_access_grants (visitor_id CASCADE)
          └─< badges             (visitor_id CASCADE; jti UNIQUE)

zones ─┬─< zone_access_grants  (zone_id CASCADE)
       └─< access_events       (zone_id SET NULL)

access_events.subject_id → users.id OR visitors.id (polymorphic, no FK; subject_type enum)
zone_access_grants: CHECK exactly one of (user_id, visitor_id) is set
```

| Table | Key columns |
| --- | --- |
| `users` | `email` (unique), `role`, `clearance`, `is_active`, `mfa_enabled`, `mfa_secret_encrypted`, `failed_login_count`, `locked_until` |
| `zones` | `name` (unique), `min_clearance`, `capacity`, `current_occupancy` |
| `zone_access_grants` | `user_id` / `visitor_id`, `zone_id`, `granted_by`, `expires_at`, `revoked_at` |
| `visitors` | `visitor_type`, `host_user_id`, `clearance`, `status`, `visit_start`, `visit_end` |
| `badges` | `visitor_id`, `jti` (unique), `issued_at`, `expires_at`, `revoked`, `last_scanned_at` |
| `access_events` | `subject_type`, `subject_id`, `zone_id`, `result`, `reason`, `ip` (INET) |
| `audit_logs` | `id` (bigserial), `prev_hash`, `entry_hash` (unique), `actor_id`, `action`, `resource`, `payload` (JSONB) |

## Quick start

Prerequisites: Docker with Compose v2, and `python3` (standard library only, used to
generate secrets).

```bash
git clone <this-repo> aegis && cd aegis

# 1. Create .env with freshly generated secrets (the app refuses to start on CHANGE_ME values).
cp .env.example .env
gen() { python3 -c "import secrets; print(secrets.token_urlsafe(48))"; }
fernet() { python3 -c "import base64, os; print(base64.urlsafe_b64encode(os.urandom(32)).decode())"; }
sed -i.bak \
  -e "s|CHANGE_ME_postgres_password|$(gen)|g" \
  -e "s|CHANGE_ME_redis_password|$(gen)|g" \
  -e "s|^JWT_SECRET=.*|JWT_SECRET=$(gen)|" \
  -e "s|^BADGE_HMAC_SECRET=.*|BADGE_HMAC_SECRET=$(gen)|" \
  -e "s|^MFA_ENCRYPTION_KEY=.*|MFA_ENCRYPTION_KEY=$(fernet)|" \
  .env && rm .env.bak

# 2. Build and start (runs the Alembic migration automatically).
docker compose up -d --build        # or: make up

# 3. Check it.
curl http://localhost:8080/api/health   # {"status":"ok"}
```

| URL | What you get |
| --- | --- |
| http://localhost:8080/ | React status page showing live API health |
| http://localhost:8080/api/health | `{"status":"ok"}` |

Stop with `docker compose down` (`make down`). Add `-v` to also delete the database volume.

The `fernet()` helper produces the same format as `cryptography.fernet.Fernet.generate_key()`
(32 random bytes, url-safe base64).

### Lint and test

```bash
python3.12 -m venv backend/.venv
backend/.venv/bin/pip install -r backend/requirements-dev.txt
(cd frontend && npm ci)

make lint   # ruff check, ruff format --check, mypy, bandit, oxlint
make test   # pytest with coverage (80% gate), then the frontend production build
```

Locally without a database, the 8 integration tests are **skipped** (62 passed, 8 skipped). In CI (`CI=true`) they never skip.

### Integration tests (real PostgreSQL)

These cover the trigger, the constraints, enum ordering and the migration round-trip. They
**downgrade the target database to base**, so only point them at a disposable database:

```bash
docker run -d --rm --name aegis-test-pg \
  -e POSTGRES_USER=aegis -e POSTGRES_PASSWORD=aegis -e POSTGRES_DB=aegis_test \
  -p 127.0.0.1:55432:5432 postgres:16-alpine
until docker exec aegis-test-pg pg_isready -h 127.0.0.1 -U aegis -q; do sleep 1; done
cd backend && AEGIS_TEST_DATABASE_URL=postgresql+psycopg://aegis:aegis@127.0.0.1:55432/aegis_test \
  .venv/bin/pytest -m integration -v
docker stop aegis-test-pg
```

`make seed` and `make bench` are deliberately disabled: they print "not implemented yet" and
exit non-zero.

## Threat model (STRIDE)

Scoped to what exists plus what's planned. **Implemented** means it is in the code and was
verified. **Planned** means it is not built.

| STRIDE | Threat | Mitigation | Status |
| --- | --- | --- | --- |
| **S**poofing | Someone calls the API as another user | JWT access/refresh tokens, argon2 password hashing, TOTP MFA | **Planned**: there is no authentication yet |
| Spoofing | Deployment runs with default/weak secrets | Startup rejects missing, short (<32), or `CHANGE_ME` secrets and invalid Fernet keys; compose refuses empty secret vars | Implemented |
| Spoofing | Direct access to DB or Redis | Both on an `internal: true` network with no published ports; Redis `requirepass` | Implemented |
| **T**ampering | Audit history edited or erased | `audit_log_immutable` trigger blocks UPDATE, DELETE and TRUNCATE | Implemented |
| Tampering | Inconsistent or forged rows (grant for two subjects, occupancy > capacity, malformed hash) | DB `CHECK` constraints, native enums, FK rules | Implemented |
| Tampering | Audit rows inserted out of chain | SHA-256 hash chain writer and verifier | **Planned**: the table exists, but nothing writes or verifies the chain |
| **R**epudiation | User denies an action or an access attempt | `audit_logs` and `access_events` written by the app on every action | **Planned**: schema exists, no writers yet |
| **I**nformation disclosure | Secrets leaked via logs or errors | `SecretStr`, `hide_input_in_errors` (tested) | Implemented |
| Information disclosure | Clickjacking, MIME sniffing, XSS impact | CSP, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy` at the edge | Implemented |
| Information disclosure | API schema exposed in production | `/api/docs` and `/api/openapi.json` disabled when `ENVIRONMENT=production` | Implemented |
| Information disclosure | TOTP secrets readable from the DB | Fernet-encrypted `mfa_secret_encrypted` | **Planned**: the key is validated at startup, but no encryption code exists |
| Information disclosure | Secrets committed to git | `.env` gitignored; gitleaks on every push/PR; per-run random CI secrets | Implemented. gitleaks' first run caught a committed dummy CI key, which is now removed and allowlisted by exact fingerprint only |
| **D**enial of service | Request floods | nginx `limit_req` (20 r/s burst 40 on `/api/`; 5 r/min on the future login path), 1 MB body cap | Implemented (edge) |
| Denial of service | Per-user/per-route abuse behind the proxy | Redis-backed app rate limiting | **Planned**: settings exist, no code |
| **E**levation of privilege | Container breakout or privilege gain | Non-root in all 5 services, `no-new-privileges`; `cap_drop: ALL` and read-only rootfs on backend/frontend/edge | Implemented |
| Elevation of privilege | Personnel reaching Admin or SecurityOfficer functions, or entering zones above their clearance | Role checks, plus a policy engine requiring `is_active` ∧ `clearance.satisfies(zone.min_clearance)` ∧ an unexpired grant | **Planned**: only the building blocks exist (`Clearance.satisfies`, `ZoneAccessGrant.is_valid_at`) |

### Known limitations (honest list)

- **The trigger can be bypassed by the table owner or a superuser.** They can
  `ALTER TABLE … DISABLE TRIGGER`, set `session_replication_role = replica`, or `DROP` the
  table. **In the current compose setup the backend connects as `POSTGRES_USER`, which the
  official image makes a superuser and which owns the tables.** So the trigger stops
  mistakes and plain SQL, but not a compromised app credential. Fix (planned): run the app
  as a separate role with only `INSERT`/`SELECT` on `audit_logs`.
- **Email uniqueness is case-sensitive** (`Alice@x.io` and `alice@x.io` can both exist).
  Planned fix: normalise in the service layer or use `citext`.
- **Redis is single-node** with AOF persistence and no replication or Sentinel, and the app
  does not use it yet.
- **CI fixes not yet confirmed on GitHub.** The first run failed for two reasons. gitleaks
  flagged a dummy key hardcoded in the workflow, and `aquasecurity/trivy-action@0.28.0` no
  longer resolved, because its tags were migrated to a `v` prefix after a supply-chain attack.
  A local reproduction also showed the old frontend base image (`nginx-unprivileged:1.27-alpine`,
  Alpine 3.21.3) had 58 fixable HIGH/CRITICAL CVEs. All three are fixed and verified locally
  with the same tool versions; the next push is the first real test.
- **The compose edge proxy uses the upstream nginx image unmodified**, and CI only scans the
  images it builds. Trivy 0.70.0 currently reports 3 fixable HIGH CVEs in it (`curl`/`libcurl`,
  `brotli-libs`) that upstream hasn't rebuilt for yet. The frontend image patches these with
  `apk upgrade`; the edge container does not.
- **CI ignores CVEs that have no fix yet** (`ignore-unfixed: true`). The backend image
  currently carries 61 such HIGH/CRITICAL findings, all from the Debian 12 base image
  (53 `affected`, 7 `fix_deferred`, 1 `will_not_fix`; mostly `util-linux` libraries). They
  fail the gate automatically once Debian ships a fix. Moving to `python:3.12-slim-trixie`
  measured 44 instead of 61, which helps but isn't a fix; it's a candidate follow-up.
- **Coverage is measured over code that exists.** The 31 placeholder modules have no
  statements, so they neither add to nor subtract from the percentage.
- **Swagger UI won't render through the edge.** In non-production, `/api/docs` returns 200,
  but it loads its JS/CSS from `cdn.jsdelivr.net`, which the edge CSP (`script-src 'self'`)
  doesn't allow. Inferred from the CSP and the page source; not browser-tested.
  `/api/openapi.json` works.
- **Security headers are sent twice on `/`.** Both the edge nginx and the frontend nginx add
  `X-Content-Type-Options`, `X-Frame-Options` and `Referrer-Policy`. The values are
  identical, but it is redundant.
- **No documented non-Docker dev server yet.** Only the Docker path and the test commands
  above are verified.
